# Agent Note: Fork-local CI trim for OpScaleHub/deepseek-harness

Status: implemented

English | [中文](2026-08-16-fork-ci-trim.zh.md)

## Problem

OpScaleHub/deepseek-harness is a straight fork and inherited every upstream GitHub Actions workflow unchanged. Several of them assume state that only exists on `deepseek-ai/deepseek-harness` and its organization: [ci.yml](../../../../.github/workflows/ci.yml)'s enterprise, native-Windows, and self-hosted-standby jobs target the organization-owned `dsh-ubuntu-24-04-*`/`dsh-windows-2025-*` larger-runner pools or the self-hosted `vm-backup`/`dsh-win-ci` VMs described in [the CI failover runbook](2026-07-26-ci-failover-runbook.md) and [the native-Windows pull-request CI note](2026-08-08-native-windows-pull-request-ci.md); [issue-lifecycle.yml](../../../../.github/workflows/issue-lifecycle.yml) hardcodes `owner: deepseek-harness` and needs the `DSH_ISSUE_APP_CLIENT_ID`/`DSH_ISSUE_APP_PRIVATE_KEY` GitHub App credentials; [issue-policy.yml](../../../../.github/workflows/issue-policy.yml) runs `.github/issue-management/policy.mjs`, whose `config.json` hardcodes organization `deepseek-harness` and GitHub Project number 1 with its own custom fields and statuses; [docs-pages.yml](../../../../.github/workflows/docs-pages.yml) calls `actions/configure-pages`, which fails without GitHub Pages enabled on the repository. None of these five conditions hold on the fork. The fork has zero self-hosted runners registered and no admin access to the upstream organization's larger-runner pools, so every pull request queued behind the enterprise Linux jobs and `windows-native` for 65+ minutes waiting for capacity that could never arrive, while `issue-lifecycle` and `issue-policy` failed outright on every issue and pull-request event.

## Decision

[ci.yml](../../../../.github/workflows/ci.yml)'s pull-request-triggered `jobs:` now has exactly two entries: `static` (`pnpm run check:ci:static` — the existing static/docs/knip/module-graph aggregate, including the translation-pairing and `docs:check` gates that fire on every bilingual-docs PR) and `unit` (`pnpm run test`, the uninstrumented Vitest run), both on plain `ubuntu-latest` with `setup-node`'s built-in `cache: pnpm`. They replace `node-24`, `node-24-coverage`, `node-24-consumers`, `node-compat`, `python-sdk`, `python-runtime`, `windows` (Wine), `wine-apt-cache`, and `windows-native`. `all-checks-passed.needs` reads `[static, unit]`, and its `runs-on` drops the `DSH_CI_FAILOVER_LINUX`-selecting expression down to a plain `ubuntu-latest`, since there is no failover pool to select. The push-triggered self-hosted standby drills `serial-linux-selfhosted` and `serial-windows` are removed outright — no `vm-backup` or `dsh-win-ci` VM exists on this fork to drill. The already-dormant `serial-linux`/`serial-macos` (`if: false`) and the `workflow_dispatch`-only `larger-runner-benchmark`/`consolidated-runner-benchmark` are left in place: they cost nothing unless someone re-enables or dispatches them, and a short comment now says so at each site. The top-of-file concurrency comment and a stale in-job comment inside the dormant `serial-linux` job are reworded to stop describing standby drills and enterprise jobs this file no longer has.

[issue-lifecycle.yml](../../../../.github/workflows/issue-lifecycle.yml) and [issue-policy.yml](../../../../.github/workflows/issue-policy.yml) keep their job bodies untouched and drop their `issues`/`pull_request`/`pull_request_review` triggers down to `workflow_dispatch` only, with a comment naming the exact upstream-owned state (the GitHub App credentials; the hardcoded organization and GitHub Project) that blocks them here. [docs-pages.yml](../../../../.github/workflows/docs-pages.yml) similarly drops its path-filtered `push` trigger to `workflow_dispatch` only, with a comment that restoring the `push` trigger is the entire re-enable once GitHub Pages is turned on for the repository. [container-publish.yml](../../../../.github/workflows/container-publish.yml) is unchanged: it already targets only this repository's own GHCR namespace via the repo-scoped `GITHUB_TOKEN` and passed as designed on PR #1.

`release.yml`, `release-vendor.yml`, `sandbox.yml`, `landlock-run.yml`, `landlock-run-release.yml`, `e2b-e2e.yml`, `pi-ai-provider-e2e.yml`, `expected-filenames.yml`, `build-exe-for-python-sdk.yml`, and `e2e.yml` are reviewed and left untouched. `release.yml` and `release-vendor.yml` run on every pull request and master push but only ever use standard `ubuntu-24.04`, so they already pass without queueing. `sandbox.yml` is master-push-only and its matrix (`ubuntu-latest`, `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-latest`) is entirely standard-hosted. `landlock-run.yml`'s matrix comes from `native/landlock-run/scripts/github-matrix.mjs`, which only ever names `ubuntu-24.04`/`ubuntu-24.04-arm`, and it is path-filtered to `native/landlock-run/**`, which this fork does not touch. `landlock-run-release.yml`, `e2b-e2e.yml`, and `pi-ai-provider-e2e.yml` are already `workflow_dispatch`-only. `expected-filenames.yml` is path-filtered to golden-file names. `build-exe-for-python-sdk.yml`'s matrix uses only `ubuntu-latest`/`ubuntu-24.04-arm`/`macos-latest`; its only automatic trigger going forward is the `python-release-dry-run` PR label, which this fork does not apply. `e2e.yml` runs on every pull request but is designed to self-skip as a successful check when its `DEEPSEEK_API_KEY_EXTERNAL` secret is absent, which it is on this fork.

## Alternatives considered

**Fix `.github/issue-management/config.json` and `policy.mjs` to target `OpScaleHub/deepseek-harness` instead of disabling `issue-lifecycle`/`issue-policy`.** Rejected: the scripts assume a GitHub Project (`projectNumber: 1`) with its own custom fields and status set, plus a dedicated GitHub App, that only exist upstream. Replicating that apparatus is not justified by the fork's stated "file issues, developer agents implement, this account reviews and merges" workflow, and no such Project exists on the fork today.

**Set the `DSH_CI_FAILOVER_LINUX`/`DSH_CI_FAILOVER_WINDOWS` repository variables to retarget the enterprise and native-Windows jobs instead of removing them.** Rejected: those variables only switch between two upstream-owned pools each (organization larger runners vs. self-hosted VMs); neither branch resolves to anything that exists on this fork, so there is no configuration-only fix.

**Delete `issue-lifecycle.yml`, `issue-policy.yml`, and `docs-pages.yml` outright instead of gating them behind `workflow_dispatch`.** Rejected: keeping the files present but inert means re-enabling any of them (wiring an OpScaleHub-owned GitHub App and Project, enabling Pages) is a configuration change plus reverting one `on:` block, not re-adding deleted job logic, and keeps the [issue's stated goal](https://github.com/OpScaleHub/deepseek-harness/issues/2) of staying upstream-compatible intact.

**Run the removed coverage/consumers/node-compat/Windows suites unsharded on `ubuntu-latest` instead of dropping them from the pull-request trigger.** Rejected: those gates were worker-count-tuned for a 16-core pool (`DSH_COVERAGE_MAX_WORKERS`, `DSH_SNAPSHOT_MAX_CONCURRENCY`, and similar), and running them uninstrumented on a standard runner would multiply pull-request latency for a fork whose explicit goal is a fast, minimal, always-resolvable verdict. `pnpm run test` covers the same product code in a small fraction of the time; `check:ci:coverage`, `check:ci:consumers`, `check:node-compat`, and `check:ci:windows-complete` remain unmodified `package.json` scripts that a contributor can still run locally, or that a later PR can wire back into `ci.yml` unmodified if this fork gains equivalent runner capacity.

## Consequences

Pull requests on this fork get a real, fast, always-resolvable verdict (`static` + `unit`, both on standard runners) instead of queueing behind capacity that never materializes. Issue and pull-request events stop producing an automatic failing check from `issue-lifecycle`/`issue-policy`. `container-publish.yml` continues to build and publish `ghcr.io/opscalehub/deepseek-harness` on master pushes and `dsh-v*` tags exactly as before.

The fork gives up automatic per-pull-request enforcement of the 100%-per-file coverage threshold, the Node 22.19/26 compatibility matrix, the keyless Python SDK suite, and both Windows lanes (Wine-blocking and native-complete). None of the underlying gate scripts changed, so every one of them remains runnable by hand (`pnpm run check:ci:coverage`, `check:node-compat`, `check:ci:windows-complete`, `check:ci:consumers`) and restorable into `ci.yml` without modification if runner capacity changes. `docs-pages.yml` no longer auto-deploys the documentation site on doc changes until GitHub Pages is enabled and its `push` trigger is restored.

`.github/workflows/ci.yml`, `issue-lifecycle.yml`, `issue-policy.yml`, and `docs-pages.yml` are now fork-local overrides of upstream-owned files. A future `git merge`/`git rebase` bringing in `deepseek-ai/deepseek-harness` history that touches any of these four files should keep this fork's version and re-apply any genuinely new upstream job or gate by hand rather than take upstream's file wholesale.

This is a bounded, deliberate exception to [keeping an implemented Agent Note current with what shipped](../AGENTS.md): [the CI failover runbook](2026-07-26-ci-failover-runbook.md), [the native-Windows pull-request CI note](2026-08-08-native-windows-pull-request-ci.md), and [the pnpm/action-setup caching note](2026-07-26-pnpm-action-setup-for-symmetric-ci-caching.md) are left unedited by this change and continue to name jobs (`node-24`, `node-compat`, `windows-native`, `serial-windows`, and others) that no longer exist in this fork's own `ci.yml`. Rewriting three heavily cross-referenced upstream investigation records to match a fork-local operational choice would itself create the reconciliation conflicts [the originating issue](https://github.com/OpScaleHub/deepseek-harness/issues/2) asked this note to avoid, and none of the three is archived, since their content remains current for upstream's own shipped `ci.yml`. Treat their job-name references as describing upstream's design, not this fork's `ci.yml`, until a future reconciliation either restores the matching capacity or intentionally supersedes them. `container-publish.yml` and its `web-bind-all.patch.yml` overlay have no upstream counterpart and need no reconciliation policy.
