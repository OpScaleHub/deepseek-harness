# Agent Note: Fork-local CI trim for OpScaleHub/deepseek-harness

Status: implemented

English | [中文](2026-08-16-fork-ci-trim.zh.md)

## Problem

OpScaleHub/deepseek-harness is a straight fork and inherited every upstream GitHub Actions workflow unchanged. Several of them assume state that only exists on `deepseek-ai/deepseek-harness` and its organization: [ci.yml](../../../../.github/workflows/ci.yml)'s enterprise, native-Windows, and self-hosted-standby jobs target the organization-owned `dsh-ubuntu-24-04-*`/`dsh-windows-2025-*` larger-runner pools or the self-hosted `vm-backup`/`dsh-win-ci` VMs described in [the CI failover runbook](2026-07-26-ci-failover-runbook.md) and [the native-Windows pull-request CI note](2026-08-08-native-windows-pull-request-ci.md); [issue-lifecycle.yml](../../../../.github/workflows/issue-lifecycle.yml) hardcodes `owner: deepseek-harness` and needs the `DSH_ISSUE_APP_CLIENT_ID`/`DSH_ISSUE_APP_PRIVATE_KEY` GitHub App credentials; [issue-policy.yml](../../../../.github/workflows/issue-policy.yml) runs `.github/issue-management/policy.mjs`, whose `config.json` hardcodes organization `deepseek-harness` and GitHub Project number 1 with its own custom fields and statuses; `docs-pages.yml` calls `actions/configure-pages`, which fails without GitHub Pages enabled on the repository; [e2e.yml](../../../../.github/workflows/e2e.yml)'s `push`/`schedule` triggers assume the `DEEPSEEK_API_KEY_EXTERNAL` repository secret described in [the real-API e2e CI note](../testing/2026-06-19-real-api-e2e-ci.md), which this fork has never configured. None of these six conditions hold on the fork. The fork has zero self-hosted runners registered and no admin access to the upstream organization's larger-runner pools, so every pull request queued behind the enterprise Linux jobs and `windows-native` for 65+ minutes waiting for capacity that could never arrive, while `issue-lifecycle` and `issue-policy` failed outright on every issue and pull-request event and `e2e.yml`'s preflight step hard-failed on every push to master and every nightly schedule run (confirmed via `gh run list`: a `push`-triggered `E2E (real DeepSeek API)` run failing in 1m3s). `e2e.yml`'s own `pull_request` trigger was already safe by construction: GitHub reports `head.repo.fork` as true for every pull request in this repository, because the repository itself is a fork of `deepseek-ai/deepseek-harness`, so the job's existing untrusted-PR skip condition already covered every pull request here regardless of author.

## Decision

[ci.yml](../../../../.github/workflows/ci.yml) is rewritten from a clean base rather than patched: one `ci` job on plain `ubuntu-latest`, triggered only by `pull_request`, running `pnpm run check:ci:static` (the existing static/docs/knip/module-graph aggregate, including the translation-pairing and `docs:check` gates that fire on every bilingual-docs PR) then `pnpm run test` (the uninstrumented Vitest run), with `setup-node`'s built-in `cache: pnpm`. This replaces the entire upstream tail in one pass: `node-24`, `node-24-coverage`, `node-24-consumers`, `node-compat`, `python-sdk`, `python-runtime`, `windows` (Wine), `wine-apt-cache`, `windows-native`, the push-triggered self-hosted standby drills `serial-linux-selfhosted`/`serial-windows`, the already-dormant `serial-linux`/`serial-macos` (`if: false`), the `workflow_dispatch`-only `larger-runner-benchmark`/`consolidated-runner-benchmark`, the `all-checks-passed` aggregate job that existed to give branch protection one stable name across a changing matrix, and the `push`/`workflow_dispatch` triggers only those removed jobs used. A single job needs no such aggregate: its own check name is already the stable one. Nothing in this file references `DSH_CI_FAILOVER_LINUX`, a larger-runner pool, or a self-hosted VM.

[issue-lifecycle.yml](../../../../.github/workflows/issue-lifecycle.yml) and [issue-policy.yml](../../../../.github/workflows/issue-policy.yml) keep their job bodies untouched and drop their `issues`/`pull_request`/`pull_request_review` triggers down to `workflow_dispatch` only, with a comment naming the exact upstream-owned state (the GitHub App credentials; the hardcoded organization and GitHub Project) that blocks them here. `docs-pages.yml` similarly drops its path-filtered `push` trigger to `workflow_dispatch` only, with a comment that restoring the `push` trigger is the entire re-enable once GitHub Pages is turned on for the repository. [container-publish.yml](../../../../.github/workflows/container-publish.yml) is unchanged: it already targets only this repository's own GHCR namespace via the repo-scoped `GITHUB_TOKEN` and passed as designed on PR #1.

[e2e.yml](../../../../.github/workflows/e2e.yml) drops its `push: branches: [main, master]` and nightly `schedule` triggers, keeping `pull_request` and `workflow_dispatch`. The job's own `if:` only ever guarded `pull_request` (skipping untrusted forks and Dependabot, where GitHub withholds secrets); `push` and `schedule` had no such guard and always ran, so the preflight step's deliberate hard-fail-when-missing design (added specifically to prevent a missing secret from reporting a false green) fired on every push to master and every nightly run. `workflow_dispatch` keeps its unconditional preflight fail: a human explicitly dispatching this workflow should get a loud, specific failure if the secret is still unconfigured, not a silent skip. The job's steps, its `pull_request_target` security rationale, and the untrusted-PR skip condition are all unchanged.

`release.yml`'s and `release-vendor.yml`'s `pack` jobs (the ones every pull request runs, packing the dsh and vendor npm families respectively) switch from a hand-rolled `Configure pnpm store path` step plus `actions/cache/restore@v4` to `setup-node`'s built-in `cache: pnpm`, matching the `ci` job and the pattern [the pnpm/action-setup caching note](2026-07-26-pnpm-action-setup-for-symmetric-ci-caching.md) already established elsewhere. That restore-only cache was seeded by the master-only `serial-linux` job in the old `ci.yml`; `serial-linux` is `if: false` (dormant, upstream-wide, not fork-specific) and its self-hosted sibling `serial-linux-selfhosted` never had a runner to execute on this fork either, so the cache these two `pack` jobs restored from has never actually been populated here — every pull request paid a fully cold `pnpm install`. `setup-node`'s `cache: pnpm` is self-contained (each job saves what it restores), so this fixes the miss without depending on a producer job. Their triggers, runner (`ubuntu-24.04`), and every other step are unchanged; the `publish` job in each file (manual-dispatch-only, no pnpm install of real weight) is untouched.

`sandbox.yml`, `landlock-run.yml`, `landlock-run-release.yml`, `e2b-e2e.yml`, `pi-ai-provider-e2e.yml`, `expected-filenames.yml`, and `build-exe-for-python-sdk.yml` are reviewed and left untouched. `sandbox.yml` is master-push-only and its matrix (`ubuntu-latest`, `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-latest`) is entirely standard-hosted. `landlock-run.yml`'s matrix comes from `native/landlock-run/scripts/github-matrix.mjs`, which only ever names `ubuntu-24.04`/`ubuntu-24.04-arm`, and it is path-filtered to `native/landlock-run/**`, which this fork does not touch. `landlock-run-release.yml`, `e2b-e2e.yml`, and `pi-ai-provider-e2e.yml` are already `workflow_dispatch`-only. `expected-filenames.yml` is path-filtered to golden-file names. `build-exe-for-python-sdk.yml`'s matrix uses only `ubuntu-latest`/`ubuntu-24.04-arm`/`macos-latest`; its only automatic trigger going forward is the `python-release-dry-run` PR label, which this fork does not apply.

## Alternatives considered

**Fix `.github/issue-management/config.json` and `policy.mjs` to target `OpScaleHub/deepseek-harness` instead of disabling `issue-lifecycle`/`issue-policy`.** Rejected: the scripts assume a GitHub Project (`projectNumber: 1`) with its own custom fields and status set, plus a dedicated GitHub App, that only exist upstream. Replicating that apparatus is not justified by the fork's stated "file issues, developer agents implement, this account reviews and merges" workflow, and no such Project exists on the fork today.

**Set the `DSH_CI_FAILOVER_LINUX`/`DSH_CI_FAILOVER_WINDOWS` repository variables to retarget the enterprise and native-Windows jobs instead of removing them.** Rejected: those variables only switch between two upstream-owned pools each (organization larger runners vs. self-hosted VMs); neither branch resolves to anything that exists on this fork, so there is no configuration-only fix.

**Delete `issue-lifecycle.yml`, `issue-policy.yml`, and `docs-pages.yml` outright instead of gating them behind `workflow_dispatch`.** Rejected: keeping the files present but inert means re-enabling any of them (wiring an OpScaleHub-owned GitHub App and Project, enabling Pages) is a configuration change plus reverting one `on:` block, not re-adding deleted job logic, and keeps the [issue's stated goal](https://github.com/OpScaleHub/deepseek-harness/issues/2) of staying upstream-compatible intact.

**Run the removed coverage/consumers/node-compat/Windows suites unsharded on `ubuntu-latest` instead of dropping them from the pull-request trigger.** Rejected: those gates were worker-count-tuned for a 16-core pool (`DSH_COVERAGE_MAX_WORKERS`, `DSH_SNAPSHOT_MAX_CONCURRENCY`, and similar), and running them uninstrumented on a standard runner would multiply pull-request latency for a fork whose explicit goal is a fast, minimal, always-resolvable verdict. `pnpm run test` covers the same product code in a small fraction of the time; `check:ci:coverage`, `check:ci:consumers`, `check:node-compat`, and `check:ci:windows-complete` remain unmodified `package.json` scripts that a contributor can still run locally, or that a later PR can wire back into `ci.yml` unmodified if this fork gains equivalent runner capacity.

**Configure a real `DEEPSEEK_API_KEY_EXTERNAL` repository secret instead of dropping `e2e.yml`'s `push`/`schedule` triggers.** Rejected for this change: provisioning a live external-API key that every master push and nightly run would spend is a repository-ops decision for whoever owns the fork's API budget, not a default a CI trim should make silently. Dropping the two triggers this fork cannot satisfy is reversible without any code change — adding the secret and restoring `push`/`schedule` is a configuration-only follow-up if the fork later wants real post-merge/nightly API coverage.

## Consequences

Pull requests on this fork get a real, fast, always-resolvable verdict (one `ci` job on a standard runner) instead of queueing behind capacity that never materializes. Issue and pull-request events stop producing an automatic failing check from `issue-lifecycle`/`issue-policy`, and master pushes and nightly runs stop producing an automatic failing check from `e2e.yml`. `release.yml` and `release-vendor.yml`'s `pack` jobs get a working pnpm store cache on every pull request instead of a permanent, silent miss. `container-publish.yml` continues to build and publish `ghcr.io/opscalehub/deepseek-harness` on master pushes and `dsh-v*` tags exactly as before, already caching Docker layers through BuildKit's `type=gha` backend from PR #1, unaffected by this note.

The fork gives up automatic per-pull-request enforcement of the 100%-per-file coverage threshold, the Node 22.19/26 compatibility matrix, the keyless Python SDK suite, and both Windows lanes (Wine-blocking and native-complete). None of the underlying gate scripts changed, so every one of them remains runnable by hand (`pnpm run check:ci:coverage`, `check:node-compat`, `check:ci:windows-complete`, `check:ci:consumers`) and restorable into `ci.yml` without modification if runner capacity changes. `docs-pages.yml` no longer auto-deploys the documentation site on doc changes until GitHub Pages is enabled and its `push` trigger is restored. The fork also gives up the post-merge and nightly real-API e2e signal `push`/`schedule` provided upstream; `e2e.yml`'s pull-request lane keeps proving the real DeepSeek API path on every trusted pull request (via the repo-level `head.repo.fork` skip, unchanged by this note), and restoring `push`/`schedule` is a configuration-only follow-up once `DEEPSEEK_API_KEY_EXTERNAL` is provisioned.

`.github/workflows/ci.yml`, `issue-lifecycle.yml`, `issue-policy.yml`, `docs-pages.yml`, and `e2e.yml` are now fork-local overrides of upstream-owned files. A future `git merge`/`git rebase` bringing in `deepseek-ai/deepseek-harness` history that touches any of these five files should keep this fork's version and re-apply any genuinely new upstream job or gate by hand rather than take upstream's file wholesale.

This is a bounded, deliberate exception to [keeping an implemented Agent Note current with what shipped](../AGENTS.md): [the CI failover runbook](2026-07-26-ci-failover-runbook.md), [the native-Windows pull-request CI note](2026-08-08-native-windows-pull-request-ci.md), [the pnpm/action-setup caching note](2026-07-26-pnpm-action-setup-for-symmetric-ci-caching.md), and [the real-API e2e CI note](../testing/2026-06-19-real-api-e2e-ci.md) are left unedited by this change and continue to name jobs and triggers (`node-24`, `node-compat`, `windows-native`, `serial-windows`, `e2e.yml`'s `push`/`schedule`, and others) that no longer exist or fire automatically on this fork's own workflow files. Rewriting four heavily cross-referenced upstream investigation and security-rationale records to match a fork-local operational choice would itself create the reconciliation conflicts [the originating issue](https://github.com/OpScaleHub/deepseek-harness/issues/2) asked this note to avoid, and none of the four is archived, since their content remains current for upstream's own shipped workflows. Treat their job-name and trigger references as describing upstream's design, not this fork's workflow files, until a future reconciliation either restores the matching capacity/secret or intentionally supersedes them. `container-publish.yml` and its `web-bind-all.patch.yml` overlay have no upstream counterpart and need no reconciliation policy.
